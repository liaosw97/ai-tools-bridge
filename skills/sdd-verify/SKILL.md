# sdd-verify — 全面验证

对所有 spec 场景进行逐一验证，确认实现完整性和测试覆盖率。

---

<!-- include: ../_shared/base-triggers.md -->

**触发**：用户执行 `/sdd-verify`，或说"验证""全面验证""运行所有测试""检查覆盖率"。
**不触发**：要审查代码质量（→ `/sdd-review-code`）；要归档（→ `/sdd-ship`）。
**歧义处理**：无代码变更时建议先编码（→ `/sdd-code`）。

<!-- include: ../_shared/output-constraints.md -->

## 前置逻辑（SDD 自有）

### 0. 前置校验

- **hotfix 降级检测**：如果当前 change 仅含 hotfix.md（无 proposal.md/specs//tasks.md，track=hotfix）——**不报错阻断**，降级为输出卡片状态摘要：验证命令结果（修复/回归测试）、未覆盖边界、衍生项，然后结束。
- **阻断**：`specs/` 不存在或无代码文件 → 拒绝执行，输出"缺少 spec 或代码，请先执行 /sdd-code 完成实现"

<!-- include: ../_shared/role-loading.md -->

**默认角色**: `qa-lead`
**可选角色**: `cso`, `sre`

### 1. 定位 Change 目录

- 扫描 `openspec/changes/` 找到活跃变更

### 2. 收集验证材料

- 读取 `specs/` — 所有需要验证的场景
- 读取 `tasks.md` — 任务完成状态
- 读取 `plan.md`（如有）— 实施范围

**invoke `superpowers:verification-before-completion`**

```

- 单元测试
- 集成测试
- Lint 检查
- 类型检查
- 构建验证

### 2b. Spec 验证

**invoke `openspec-verify-change`**

完成后停止 — 不要自动调用其他 skill 或继续下一个 action
输出位置 — 产物写入 openspec/changes/<name>/ 目录
```

验证变更的 spec 合规性。

## 后置逻辑（SDD 自有）

### 1. 环境依赖检测

在运行测试前，检测环境依赖是否可用：
- 如果 flow-test 无法执行（如外部依赖不可用）：
  1. 跳过流程级测试
  2. 在报告中注明："流程级测试已跳过（原因：<具体原因>）"
  3. 函数级测试独立运行，覆盖所有函数
- 如果流程级测试部分失败：
  1. 失败的流程级环节标记为"环境依赖不可用"而非"测试失败"
  2. 函数级测试仍可独立运行
  3. 整体判定使用函数级测试 100% 通过为准

### 1.5 职责边界确认

在生成测试报告前，确认函数级测试与流程级测试的职责边界：

- **函数级测试职责**：验证函数内部逻辑正确性（`f(x) === expected`），不校验参数传递兼容性
- **流程级测试职责**：验证函数间调用契约（`f` 的输出能否作为 `g` 的合法输入），校验参数类型兼容性
- **不重复原则**：函数级测试不应重复校验已在流程级测试中覆盖的参数传递契约

### 1.8 三向对齐 + test-cases 回填（M/L 重轨）

当 functions.md 与 test-cases.md 存在（M/L 重轨）时，执行三向对齐：

1. **全量回归**：运行全量测试（不只当前批次），因跨批次修改可能破坏已完成批次的契约
2. **三向对齐检查**：
   - 函数声明（functions.md）↔ 实际实现代码（**符号级 grep 验证**，非目测）
   - test-cases.md ↔ 实现：每个场景有测试、每个测试有出处
   - 逐符号 diff：声明的 vs 实现 grep 到的 vs 测试引用的
3. **回填 test-cases.md**：逐场景将状态更新为 ✓（通过）或 ✗（失败及原因）
4. **无幻觉函数升级**：从"快速检查"升级为逐符号 diff——实现/测试引用的函数必须有声明或属存量（只读依赖白名单）
5. **通过门**：声明 = 实现 = 测试覆盖，三者闭环才允许 ship

> 存量函数无声明 → 在"只读依赖"白名单中，不做"声明⊆实现"违例处理。

### 2. Scenario 覆盖率统计

逐条检查 spec 场景：

```
Scenario 覆盖率:
  spec:auth#login           ✅ 有测试覆盖
  spec:auth#logout          ✅ 有测试覆盖
  spec:auth#token-refresh   ❌ 无测试覆盖
  spec:auth#failed-login    ⚠️ 测试存在但未覆盖边界值

覆盖率: 3/4 (75%)
```

### 3. 验证报告

汇总所有验证结果，按层级分别报告：

```
验证报告
═══════════════════════════════════

#### 函数级测试结果
- 通过率：N/M（XX%）
- 覆盖函数：函数名列表
- 失败详情：每个失败函数的断言和期望

#### 流程级测试结果
- 通过率：N/M（XX%）
- 验证链路：每条调用链的测试结果
- 失败详情：精确定位到具体哪个环节失败

#### 总覆盖率
- 函数覆盖率：已编写测试的函数数 / 总函数数
- 说明：覆盖率指标为参考信息，不纳入通过/失败判定

单元测试:     ✅ 42/42 通过
集成测试:     ✅ 12/12 通过
Lint:         ✅ 无错误
类型检查:     ✅ 无错误
构建:         ✅ 成功
Spec 覆盖率:  ⚠️ 75% (3/4 场景)

未覆盖场景:
  - spec:auth#token-refresh — 需要补充测试
```

### 4. 通过判定标准

- PASS：函数级测试通过率 100% 且流程级测试通过率 100%
- FAIL：函数级测试通过率 < 100% 或流程级测试通过率 < 100%
- 覆盖率不通过：覆盖率低于预设阈值时显示警告，但不改变 PASS/FAIL 状态

### 3. 完成引导

```
sdd-verify 完成。

验证报告: [PASSED / FAILED]

如需释放上下文，可安全 /clear。

推荐下一步（按审查结果）:
  1. ★ /sdd-ship — PASSED，归档合并
  2. ○ /sdd-test-code — FAILED，测试未覆盖场景
  3. ○ /sdd-code — FAILED，实现缺失
```
